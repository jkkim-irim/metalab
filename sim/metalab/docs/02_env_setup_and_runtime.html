MetaLab — 환경 생성부터 런타임까지

엔진 설치(로컬·AWS) · Hub↔Spoke · Runtime(env_driver) — genesis / newton 스포크 기준

TL;DR — “genesis/newton 전용 환경은 어떻게 만들어지나?”

이미지/스냅샷을 굽지 않는다. 각 엔진의 uv.lock 을 uv sync 로 재현할 뿐이고, 이 방식은 로컬과 AWS 노드가 동일하다. 옛 conda-pack S3 스냅샷(“env snap”)은 레거시 isaaclab 경로 전용이며 은퇴(retired)됐다 — “the lockfile is the artifact.” 따라서 “환경 생성 과정”은 이미 리포 안에 있다: sim/metalab/setup.shsim/metalab/<engine>/pyproject.toml + uv.locksim_versions.envlearning/scripts/local/setup_env.sh

0큰 그림 — 디렉토리와 3단계

MetaLab(sim/metalab/)은 엔진과 무관한 계약서(Hub) 하나를 정의하고, 엔진별 파서(Spoke)가 그것을 읽어 각 시뮬레이터의 씬을 만든다. 실제 엔진 소스는 리포의 형제(sibling) 경로에 clone 되어 각자의 uv 환경에 editable 로 설치된다. 

allex_ws/                         ← 워크스페이스 (리포의 부모)
├─ allex/                        ← 이 리포
│  └─ sim/
│     ├─ metalab/
│     │  ├─ api/   envs/         ← Hub: 엔진무관 계약서 + primitives  (task.py → EnvSpec)
│     │  ├─ runtime/             ← env_driver.py (EnvSpec+backend → VecEnv)
│     │  ├─ genesis/parser.py    ← Spoke: Genesis 파서 + backend + server (+ env/ = uv 프로젝트)
│     │  ├─ newton/parser.py     ← Spoke: Newton  파서 + backend + server (+ env/ = uv 프로젝트)
│     │  ├─ sim_versions.env     ← 업스트림 버전 핀 (SSOT)
│     │  └─ setup.sh             ← 원클릭 온보딩
│     └─ service/                ← RPC + CUDA-IPC 프로세스 경계 (cross-sim 공유)
├─ newton/                       ← git clone (업스트림, editable) — sim_versions.env 로 핀
└─ genesis-world/                ← git clone (업스트림, editable) — sim_versions.env 로 핀

이하 ① 환경 생성 → ② Hub↔Spoke 연결 → ③ 런타임 순.

1환경 생성 — sim/metalab/setup.sh 하나로 자동

목표 한 줄: genesis용·newton용 격리된 파이썬 환경(venv) 2개를 만드는 것. 명령 하나 — sim/metalab/setup.sh — 로 끝난다.

핵심 원리: 엔진 소스는 버전을 고정해 리포 외부에 git clone 하고, 파이썬 환경은 uv.lock(설치될 모든 패키지의 정확한 버전을 담은 잠금파일)으로 재현한다. 소스 버전과 잠금파일이 같으면 로컬이든 AWS 노드든 동일한 환경이 재현되며, 별도의 이미지나 스냅샷을 만들 필요가 없다.

프레시 클론된 리포에서 sim/metalab/setup.sh 를 실행하면, 두 엔진(newton·genesis) 각각에 대해 아래 3단계를 자동으로 한다(실제 작업은 learning/scripts/local/setup_env.sh 가 담당):

끝나면 서로 격리된 두 환경이 생긴다: ~/.metalab/venvs/genesis 와 ~/.metalab/venvs/newton — 각각 그 엔진 + 학습에 필요한 파이썬 패키지가 담겨 있다. genesis만, 또는 newton만 만들 수도 있다(그게 “newton-only 환경”).

엔진은 “editable sibling” — 파일이 아니라 소스로 연결

각 엔진 uv 프로젝트(sim/metalab/<engine>/pyproject.toml)는 업스트림 소스를 editable 로 참조한다: 

[tool.uv.sources]
genesis-world = { path = "../../../../genesis-world", editable = true }   # genesis
newton        = { path = "../../../../newton",        editable = true }   # newton
torch         = { index = "pytorch-cu128" }        # torch==2.10.0 (CUDA cu128)
# newton 은 추가로 NVIDIA 인덱스의 warp-lang dev 빌드를 핀

즉: 엔진 소스는 리포에 baked-in 되지 않는다. clone 되어 editable 로 붙고, 파이썬 deps만 uv.lock 에서 재현된다. 이 lockfile이 곧 재현 artifact — 별도 이미지/스냅샷을 만들지 않는다. (주석 원문: “snapshot_env.sh is retired — the lockfile is the artifact.”)

2Hub ↔ Spoke — 계약서 한 장을 각 엔진이 읽는다

Hub는 엔진무관 계약서(sim/metalab/contract 의 task.py + _api)를 load_task() 로 검증해 EnvSpec 으로 만든다. 각 엔진 server.py 는 그 엔진의 uv venv 안에서 실행되며, editable로 설치된 엔진을 import하고 파서가 EnvSpec을 읽어 씬을 만든다.

Hub — 계약서(엔진무관)
sim/metalab/contract task.py + _api  →  load_task()  →  EnvSpec
Genesis Spoke
genesis/server.py → genesis_parser.build_scene(EnvSpec) → GenesisBackend
venv ~/.metalab/venvs/genesis 에서 import genesis (editable sibling)
Newton Spoke
newton/server.py → newton_parser.build_scene(EnvSpec) → NewtonBackend
venv ~/.metalab/venvs/newton 에서 import newton (editable sibling)

build_env() 의 실제 흐름(genesis 예시, newton도 대칭):

spec     = load_task(task)                 # 계약서 → EnvSpec (엔진무관)
import genesis as gs                        # ← 그 venv의 editable sibling
handles  = genesis_parser.build_scene(spec, num_envs, viz, …)   # EnvSpec → gs.Scene
backend  = GenesisBackend(spec, handles, …)                    # 엔진을 SimBackend 뒤로
driver   = EnvDriver(spec, backend, max_episode_length=…)      # → VecEnv
# → RpcServer 로 서빙 (RPC + CUDA-IPC 경계; 핫패스 obs/action은 GPU 공유버퍼)

핵심: Hub(EnvSpec)는 하나, Spoke(parser+backend)는 엔진마다. 같은 MJCF 계약서를 두 파서가 각자 네이티브로 빌드하므로 두 엔진의 씬 구조가 일치한다(parity).

3로컬 vs AWS — 그리고 “env snap”의 정체

AWS GPU 노드도 로컬과 정확히 같은 방식(sibling clone + uv sync)으로 환경을 만든다. 차이는 “어디서 도느냐 / 코드를 어떻게 전달하느냐”뿐이다.

항목로컬 워크스테이션AWS GPU 노드 (genesis/newton)
진입sim/metalab/setup.sh → local/setup_env.shaws/rl_train.sh → (노드에서) local/rl_train.sh → local/setup_env.sh
엔진 소스sibling에 git clone + 핀 checkout동일 — 노드에서 clone (baked-in 아님)
파이썬 envuv sync → ~/.metalab/venvs/<engine>동일 — 노드에서 uv sync
코드 전달로컬 리포 그대로S3 tarball …/metalab/_deploy/allex-repo.tgz → 노드 /home/ubuntu/allex
접속/실행직접 shellkeyless SSM(AWS-RunShellScript), detached setsid
베이스 이미지—범용 DLAMI(NVIDIA 드라이버 포함) — 엔진 env는 매번 노드에서 빌드
conda / S3 스냅샷안 씀안 씀 (레거시 isaaclab만 씀)

“env snapshot”은 레거시 isaaclab 전용 (은퇴)

질문에 나온 “env snap”은 sim/isaaclab/scripts/snapshot_env.sh 가 굽는 conda-pack tar다 (env_isaaclab.tar + isaaclab.tar → s3://…/chrisryu/sim_rl/envsnap). 이건 레거시 isaaclab RPC 경로 전용이고, 현재 스포크(genesis/newton)에는 쓰이지 않는다. 여러 곳에서 명시적으로 은퇴를 선언한다:

  • setup_env.sh: “Replaces the old conda-pack-from-S3 restore; snapshot_env.sh is retired — the lockfile is the artifact.”
  • sim/metalab/{genesis,newton}/pyproject.toml: “uv sync reproduces the exact env from uv.lock — replacing the old conda-pack S3 snapshot.”
  • sim/metalab/README.md(버전 업 절): “No S3 snapshot to rebuild — the lockfile is the reproducible artifact.”

로컬·AWS 모두 검증 완료. 로컬뿐 아니라 AWS GPU 노드 경로(노드 부트스트랩 + 노드에서 uv sync)도 검증됐다 — 두 경로 모두 같은 uv.lock 으로 재현되고, conda-pack S3 스냅샷 없이 동작한다. 즉 “어디서 도느냐”만 다를 뿐, 환경을 만드는 방법은 로컬과 AWS가 동일하다.

4Runtime — env_driver 의 역할

EnvDriver(sim/metalab/runtime/env_driver.py)는 EnvSpec + SimBackend → VecEnv 어댑터다. 트레이너가 기대하는 VecEnv 인터페이스(num_envs·num_actions·device·get_observations·step·reset·seed)를 duck-typed 로 만족시키며, 엔진은 SimBackend 뒤에 숨는다(러너는 엔진을 모른다).

매 step이 하는 일:

  1. action — 정책 출력 → (EMA/커맨드 지연) 디코드 → backend.step()
  2. obs / reward / terminate — 계약서의 term 함수들이 backend 를 state 로 읽어 계산 (순수 함수, 엔진 import 없음)
  3. events(DR) / curriculum / action-delay — reset·interval 훅, done-reset 경계에서 커리큘럼
  4. per-term 종료 추적(Termination/<name> 로그) + teacher용 privileged obs 컨텍스트(EnvDriver)
계약서(.py) ─load_task→ EnvSpec ─parser→ 엔진 씬 ─backend→ [ EnvDriver = VecEnv ]
                                                              │  step: action→backend→obs/reward/terminate
                                                              ▼
                                          트레이너(PPO, in-process) ── RPC + CUDA-IPC 경계

term(obs/reward/terminate)은 backend 를 통해서만 상태를 읽으므로 엔진에 독립적이다. 따라서 같은 EnvDriver 코드가 genesis·newton 어느 backend와도 동작한다.
